title: "Команды"

Это справочник по slash-командам OpenSpec. Они вводятся в чате с ИИ-ассистентом для программирования (например, Claude Code, Cursor или Devin Desktop).

Шаблоны рабочих процессов и рекомендации по использованию команд см. в разделе [Рабочие процессы](/ru-RU/workflows/). Команды CLI описаны в разделе [CLI](/ru-RU/cli/).

В этой документации в качестве основного формата используется `/opsx:<command>`.
Некоторые инструменты используют другой вариант: Cursor и GitHub Copilot
регистрируют `/opsx-propose`, а Codex — `$openspec-propose`. Поэтому проверьте,
какой формат подходит вашему инструменту, в разделе [Вызов команд](/ru-RU/supported-tools/#вызов-команд).
В файлах, создаваемых OpenSpec, уже используется правильный вариант.

## Краткий справочник

### Быстрый путь по умолчанию (профиль `core`)

| Команда | Назначение |
|---------|---------|
| `/opsx:propose` | Создать изменение и за один шаг подготовить артефакты планирования |
| `/opsx:explore` | Обдумать идеи до начала изменения |
| `/opsx:apply` | Выполнить задачи изменения |
| `/opsx:update` | Изменить артефакты планирования и сохранить их согласованность |
| `/opsx:sync` | Объединить дельта-спецификации с основными |
| `/opsx:archive` | Архивировать завершённое изменение |

### Команды расширенного процесса (пользовательский выбор рабочего процесса)

| Команда | Назначение |
|---------|---------|
| `/opsx:new` | Создать каркас нового изменения |
| `/opsx:continue` | Создать следующий артефакт с учётом зависимостей |
| `/opsx:ff` | Быстрый переход: создать все артефакты планирования сразу |
| `/opsx:verify` | Проверить соответствие реализации артефактам |
| `/opsx:bulk-archive` | Архивировать несколько изменений сразу |
| `/opsx:onboard` | Пошагово пройти весь рабочий процесс |

По умолчанию используется глобальный профиль `core`. Чтобы включить расширенные команды рабочего процесса, запустите `openspec config profile`, выберите процессы и затем выполните `openspec update` в проекте.

## Справочник команд

### `/opsx:propose`

Создать новое изменение и подготовить артефакты планирования за один шаг. Это стандартная команда начала работы в профиле `core`.

**Syntax:**
```text
/opsx:propose [change-name-or-description]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name-or-description` | Нет | Имя в kebab-case или краткое описание изменения обычными словами |

**Что делает команда:**
- создаёт `openspec/changes/<change-name>/`;
- подготавливает артефакты, необходимые до начала реализации (для `spec-driven`: proposal, specs, design, tasks);
- останавливается, когда изменение готово к `/opsx:apply`.

**Example:**
```text
Вы: /opsx:propose add-dark-mode

ИИ:  Создана папка openspec/changes/add-dark-mode/
     ✓ proposal.md
     ✓ specs/ui/spec.md
     ✓ design.md
     ✓ tasks.md
     Готово к реализации. Запустите /opsx:apply.
```

**Советы:**
- используйте эту команду для самого быстрого полного цикла;
- если нужен пошаговый контроль артефактов, включите расширенный процесс и используйте `/opsx:new` вместе с `/opsx:continue`.

### `/opsx:explore`

> **Если не уверены, начните отсюда.** Explore — партнёр для обдумывания без обязательств: он изучает кодовую базу, сравнивает варианты и превращает расплывчатую идею в конкретный план ещё до написания кода. Команда входит в профиль по умолчанию. Подробное обоснование и примеры см. в руководстве [Сначала исследуйте](/ru-RU/explore/).

Обдумайте идею, исследуйте проблему и уточните требования до начала изменения.

**Syntax:**
```
/opsx:explore [topic]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `topic` | Нет | Тема для исследования |

**Что делает команда:**
- начинает свободное исследовательское обсуждение;
- изучает кодовую базу, чтобы отвечать на вопросы;
- сравнивает варианты и подходы;
- создаёт схемы, помогающие прояснить идею;
- сохраняет результаты по вашей просьбе или после вашего согласия: создаёт каркас изменения с помощью `openspec new change` и записывает указанные артефакты планирования либо обновляет артефакты существующего изменения;
- после прояснения идеи может перейти к `/opsx:propose` (по умолчанию) или `/opsx:new` (расширенный процесс).

**Example:**
```text
Вы: /opsx:explore

ИИ:  Что вы хотели бы исследовать?

Вы: Как организовать аутентификацию в мобильном приложении?

ИИ:  Изучу текущую настройку аутентификации...
     [анализирует кодовую базу]

     В веб-приложении используется аутентификация на основе сеансов.
     Для мобильного приложения есть три основных варианта:

     1. Токены JWT (без состояния, работают офлайн)
     2. OAuth2 (если нужен вход через стороннего поставщика)
     3. Расширить текущие сеансы (проще, но требуется подключение)

     В вашем API уже настроен CORS. Какой вариант вам ближе?

Вы: Давайте выберем JWT.

ИИ:  Это решение стоит зафиксировать. Начать изменение add-jwt-auth?
     Пока будет создана только папка изменения.

Вы: Да.

ИИ:  Создана папка openspec/changes/add-jwt-auth/. Скажите, и я подготовлю
     предложение, спецификации и задачи на основе нашего обсуждения.
```

**Советы:**
- используйте команду, если требования неясны или нужно провести исследование;
- она не пишет код и ничего не записывает, пока вы не попросите об этом или не согласитесь на её предложение;
- команда полезна для сравнения вариантов до принятия решения;
- она может читать файлы и искать по кодовой базе.

### `/opsx:new`

Создать каркас нового изменения. Команда создаёт папку изменения и ожидает, пока вы подготовите артефакты с помощью `/opsx:continue` или `/opsx:ff`.

Эта команда входит в расширенный набор рабочего процесса и не включена в профиль `core` по умолчанию.

**Syntax:**
```
/opsx:new [change-name] [--schema <schema-name>]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Имя папки изменения (если не указано, команда спросит его) |
| `--schema` | Нет | Схема рабочего процесса (по умолчанию: из конфигурации или `spec-driven`) |

**Что делает команда:**
- создаёт каталог `openspec/changes/<change-name>/`;
- создаёт файл метаданных `.openspec.yaml` в папке изменения;
- показывает шаблон первого артефакта, готового к созданию;
- запрашивает имя изменения и схему, если они не указаны.

**Что создаётся:**
```
openspec/changes/<change-name>/
└── .openspec.yaml    # Метаданные изменения (схема, дата создания)
```

**Example:**
```
Вы: /opsx:new add-dark-mode

ИИ:  Создана папка openspec/changes/add-dark-mode/
     Схема: spec-driven

     Готово к созданию: proposal
     Используйте /opsx:continue, чтобы создать его, или /opsx:ff для создания всех артефактов.
```

**Советы:**
- используйте описательные имена: `add-feature`, `fix-bug`, `refactor-module`;
- избегайте общих имён вроде `update`, `changes`, `wip`;
- схему также можно задать в конфигурации проекта (`openspec/config.yaml`).

### `/opsx:continue`

Создать следующий артефакт в цепочке зависимостей. Команда создаёт по одному артефакту для постепенного продвижения.

**Syntax:**
```
/opsx:continue [change-name]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Изменение для продолжения (если не указано, определяется по контексту) |

**Что делает команда:**
- запрашивает граф зависимостей артефактов;
- показывает, какие артефакты готовы, а какие заблокированы;
- создаёт первый готовый артефакт;
- читает файлы зависимостей для получения контекста;
- показывает, что станет доступно после создания.

**Example:**
```
Вы: /opsx:continue

ИИ:  Изменение: add-dark-mode

     Состояние артефактов:
     ✓ proposal    (готово)
     ◆ specs       (готово к созданию)
     ◆ design      (готово к созданию)
     ○ tasks       (заблокировано — нужны: specs, design)

     Создаю specs...

     [читает proposal.md и создаёт спецификации на основе требований]

     ✓ Создан openspec/changes/add-dark-mode/specs/ui/spec.md

     Теперь доступен: design
     Запустите /opsx:continue, чтобы создать следующий артефакт.
```

**Советы:**
- используйте команду, если хотите проверять каждый артефакт перед продолжением;
- она подходит для сложных изменений, требующих контроля;
- несколько артефактов могут стать готовыми одновременно;
- созданные артефакты можно редактировать до перехода дальше.

### `/opsx:ff`

Быстро пройти этап создания артефактов. Команда создаёт все артефакты планирования сразу.

**Syntax:**
```
/opsx:ff [change-name]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Изменение для быстрого перехода (если не указано, определяется по контексту) |

**Что делает команда:**
- создаёт все артефакты в порядке зависимостей;
- отслеживает выполнение с помощью списка задач;
- останавливается, когда готовы все артефакты, необходимые для `apply`;
- читает каждую зависимость перед созданием следующего артефакта.

**Example:**
```
Вы: /opsx:ff add-dark-mode

ИИ:  Быстро создаю артефакты add-dark-mode...

     ✓ Создаю proposal.md
     ✓ Создаю specs/ui/spec.md
     ✓ Создаю design.md
     ✓ Создаю tasks.md

     Все артефакты планирования готовы!
     Можно приступать к реализации. Запустите /opsx:apply.
```

**Советы:**
- используйте команду, если чётко представляете, что будете создавать;
- для простых изменений она быстрее, чем `/opsx:continue`.
- артефакты можно редактировать и после создания;
- подходит для небольших и средних функций.

---

### `/opsx:apply`

Выполнить задачи изменения. Команда проходит по списку задач, пишет код и отмечает выполненные пункты.

**Syntax:**
```
/opsx:apply [change-name]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Изменение для реализации (если не указано, определяется по контексту) |

**Что делает команда:**
- читает `tasks.md` и определяет незавершённые задачи;
- выполняет задачи одну за другой;
- при необходимости пишет код, создаёт файлы и запускает тесты;
- отмечает выполненные задачи флажком `[x]`.

**Example:**
```
Вы: /opsx:apply

ИИ:  Реализую add-dark-mode...

     Читаю tasks.md:
     - [ ] 1.1 Создать ThemeContext
     - [ ] 1.2 Добавить пользовательские свойства CSS
     - [ ] 1.3 Реализовать сохранение в localStorage

     Выполняю 1.1: создать ThemeContext...
     [создаёт src/context/ThemeContext.tsx]

     ✓ 1.1 Выполнено

     Выполняю 1.2: добавить пользовательские свойства CSS...
     [обновляет src/styles/globals.css]

     ✓ 1.2 Выполнено
     ...
```

**Советы:**
- после прерывания можно возобновить работу с того места, где вы остановились;
- для параллельных изменений указывайте имя нужного изменения;
- выполнение отслеживается флажками в `tasks.md`.

### `/opsx:update`

Изменить существующие артефакты планирования и сохранить их согласованность. Команда работает только с планом и никогда не меняет код.

**Syntax:**

```text
/opsx:update [change-name]
```

**Аргументы:**

| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Изменение для обновления (если не указано, определяется по контексту) |

**Что делает команда:**

- читает артефакты изменения с помощью `openspec status --change <name> --json`;
- применяет запрошенные правки или, если запрос не указан, проверяет артефакты на противоречия;
- согласует существующие артефакты в любом направлении (правка проектного решения может потребовать изменения предложения);
- согласовывает с вами каждую правку перед записью, по одному артефакту за раз;
- в конце рекомендует следующий шаг: `/opsx:continue` (артефакты ещё не начаты), `/opsx:apply` (перенести обновлённый план в код) или `/opsx:archive` (всё готово).

**Отсутствующие файлы:**

- Если для glob-артефакта, например `specs/**/*.md`, существует хотя бы один файл, update может предложить создать недостающий связанный файл. Команда использует инструкции схемы и просит подтвердить точный путь перед созданием.
- Артефакты, для которых ещё нет файлов, остаются для `/opsx:continue`. Намеренно пропущенные артефакты не затрагиваются.
- Новые файлы должны оставаться внутри каталога изменения. Если до создания файл появляется по подтверждённому пути, update останавливается и не перезаписывает его.

**Example:**

```text
Вы: /opsx:update add-dark-mode - теперь мы храним тему в cookie, а не в localStorage

ИИ:  Читаю артефакты add-dark-mode...

     В двух местах проектного решения упоминается localStorage; задача 1.3
     описывает сохранение в localStorage; в предложении хранилище не упомянуто.

     Предлагаемые правки:
     1. design.md — заменить localStorage на хранение в cookie
     2. tasks.md — изменить формулировку задачи 1.3 для хранения в cookie

     Применить правку 1? (design.md)
```

**Советы:**

- команда не начинает работу над артефактом, если для него ещё нет файлов. Включите `/opsx:continue` или используйте `openspec status` и `openspec instructions`, если этот необязательный процесс не установлен;
- если изменение уже реализовано, затем запустите `/opsx:apply`, чтобы привести код в соответствие с обновлённым планом;
- если правки меняют *цель* изменения, вместо этого начните новое (см. [Когда обновить изменение, а когда начать заново](/ru-RU/opsx/#когда-обновить-изменение-а-когда-начать-заново)).

### `/opsx:verify`

Проверить соответствие реализации артефактам изменения. Проверяет полноту, корректность и согласованность.

**Syntax:**
```
/opsx:verify [change-name]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Изменение для проверки (если не указано, определяется по контексту) |

**Что делает команда:**
- проверяет качество реализации по трём направлениям;
- ищет в кодовой базе подтверждение реализации;
- сообщает о проблемах, классифицируя их как CRITICAL, WARNING или SUGGESTION;
- не блокирует архивацию, но выявляет проблемы.

**Направления проверки:**

| Направление | Что проверяется |
|-----------|-------------------|
| **Полнота** | Все задачи выполнены, все требования реализованы, сценарии учтены |
| **Корректность** | Реализация соответствует цели спецификации, граничные случаи обработаны |
| **Согласованность** | Проектные решения отражены в коде, шаблоны согласованы |

**Example:**
```
Вы: /opsx:verify

ИИ:  Проверяю add-dark-mode...

     ПОЛНОТА
     ✓ Отмечены все 8 задач в tasks.md
     ✓ Для всех требований в specs есть соответствующий код
     ⚠ Сценарий «определение системных настроек» не покрыт тестами

     КОРРЕКТНОСТЬ
     ✓ Реализация соответствует цели спецификации
     ✓ Учтены граничные случаи из сценариев
     ✓ Состояния ошибок соответствуют спецификации

     СОГЛАСОВАННОСТЬ
     ✓ Проектные решения отражены в структуре кода
     ✓ Именование соответствует design.md
     ⚠ В проектном решении упомянуты «переменные CSS», а реализация использует классы Tailwind

     ИТОГ
     ─────────────────────────────
     Критические проблемы: 0
     Предупреждения: 2
     Готово к архивации: да (с предупреждениями)

     Рекомендации:
     1. Добавить тест для определения системных настроек
     2. Обновить design.md, указав использование Tailwind, или перейти на переменные CSS
```

**Советы:**
- запускайте перед архивацией, чтобы заранее найти несоответствия;
- предупреждения не блокируют архивацию, но указывают на возможные проблемы;
- проверяйте так работу ИИ перед фиксацией изменений;
- команда помогает обнаружить расхождения между артефактами и реализацией.

### `/opsx:sync`

**Необязательная команда.** Объединяет дельта-спецификации изменения с основными спецификациями. Если потребуется, archive предложит синхронизацию, поэтому обычно запускать эту команду вручную не нужно.

**Syntax:**
```
/opsx:sync [change-name]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Изменение для синхронизации (если не указано, определяется по контексту) |

**Что делает команда:**
- читает дельта-спецификации из папки изменения;
- обрабатывает разделы ADDED/MODIFIED/REMOVED/RENAMED;
- объединяет изменения с основным каталогом `openspec/specs/`;
- сохраняет существующее содержимое, не указанное в дельте;
- не архивирует изменение (оно остаётся активным).

**Example:**
```text
Вы: /opsx:sync

ИИ:  Синхронизирую дельта-спецификации add-dark-mode...

     Читаю: openspec/changes/add-dark-mode/specs/ui/spec.md
     Целевой файл: openspec/specs/ui/spec.md

     Применяемые изменения:
     ✓ ADDED: требование о выборе темы (2 сценария)
     ✓ ADDED: требование о доступности (1 сценарий)

     Выполняю слияние...
     ✓ openspec/specs/ui/spec.md обновлён

     Изменение остаётся активным. Когда будете готовы завершить его, запустите /opsx:archive.
```

**Когда использовать вручную:**

| Сценарий | Использовать sync? |
|----------|-----------|
| Длительное изменение; нужно обновить основные спецификации до архивации | Да |
| Нескольким параллельным изменениям нужны обновлённые основные спецификации | Да |
| Нужно отдельно просмотреть результат слияния | Да |
| Простое изменение, которое сразу архивируется | Нет (archive выполнит синхронизацию) |

**Советы:**
- sync выполняет интеллектуальное слияние, а не копирование и вставку;
- можно добавлять сценарии к существующим требованиям без дублирования;
- после синхронизации изменение остаётся активным и не архивируется;
- большинству пользователей не придётся запускать эту команду вручную — archive предложит синхронизацию при необходимости.

---

### `/opsx:archive`

Архивировать завершённое изменение. Команда завершает изменение и перемещает его в каталог архива.

**Syntax:**
```
/opsx:archive [change-name]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-name` | Нет | Изменение для архивации (если не указано, определяется по контексту) |

**Что делает команда:**
- проверяет состояние артефактов;
- проверяет выполнение задач и предупреждает, если остались незавершённые;
- предлагает синхронизировать дельта-спецификации, если они ещё не синхронизированы;
- перемещает папку изменения в `openspec/changes/archive/YYYY-MM-DD-<name>/`;
- сохраняет все артефакты для истории проверок.

**Example:**
```text
Вы: /opsx:archive

ИИ:  Архивирую add-dark-mode...

     Состояние артефактов:
     ✓ proposal.md существует
     ✓ specs/ существует
     ✓ design.md существует
     ✓ tasks.md существует (выполнено 8 из 8 задач)

     Дельта-спецификации ещё не синхронизированы
     → Синхронизировать сейчас? (рекомендуется)

Вы: Да.

ИИ:  ✓ Спецификации синхронизированы с openspec/specs/ui/spec.md
     ✓ Перемещено в openspec/changes/archive/2025-01-24-add-dark-mode/

     Изменение успешно архивировано.
```

**Советы:**
- незавершённые задачи не блокируют архивацию, но вызывают предупреждение;
- дельта-спецификации можно синхронизировать во время архивации или заранее;
- архивированные изменения сохраняются в истории;
- сначала выполните `/opsx:verify`, чтобы найти проблемы.

### `/opsx:bulk-archive`

Архивировать сразу несколько завершённых изменений. Команда обрабатывает конфликты спецификаций между изменениями.

**Syntax:**
```
/opsx:bulk-archive [change-names...]
```

**Аргументы:**
| Аргумент | Обязательный | Описание |
|----------|----------|-------------|
| `change-names` | Нет | Изменения для архивации (если не указаны, команда предложит выбрать) |

**Что делает команда:**
- перечисляет все завершённые изменения;
- проверяет каждое изменение перед архивацией;
- обнаруживает конфликты спецификаций между изменениями;
- разрешает конфликты, проверяя, что действительно реализовано;
- архивирует изменения в хронологическом порядке.

**Example:**
```
Вы: /opsx:bulk-archive

ИИ:  Найдено 3 завершённых изменения:
     - add-dark-mode (выполнено 8 из 8 задач)
     - fix-login-bug (выполнено 3 из 3 задач)
     - update-footer (выполнено 2 из 2 задач)

     Проверяю конфликты спецификаций...
     ⚠ add-dark-mode и update-footer затрагивают specs/ui/

     Изучаю кодовую базу для разрешения...
     Оба изменения реализованы. Объединю их в хронологическом порядке:
     1. add-dark-mode (создано 20 января)
     2. update-footer (создано 22 января)

     Архивировать все три изменения?

Вы: Да.

ИИ:  ✓ add-dark-mode архивировано
     ✓ fix-login-bug архивировано
     ✓ update-footer архивировано
     Спецификации объединены в таком порядке: add-dark-mode → update-footer
```

**Советы:**
- удобно использовать для параллельной работы;
- конфликты разрешаются агентом на основе проверки кодовой базы;
- изменения архивируются в порядке создания;
- перед перезаписью спецификаций команда запрашивает подтверждение.

### `/opsx:onboard`

Пошаговое знакомство с полным рабочим процессом OpenSpec. Интерактивное руководство на основе вашей кодовой базы.

**Syntax:**
```
/opsx:onboard
```

**Что делает команда:**
- проводит через полный цикл рабочего процесса с пояснениями;
- ищет в кодовой базе реальные возможности для улучшения;
- создаёт настоящее изменение с полноценными артефактами;
- выполняет реальную работу (небольшие безопасные изменения);
- архивирует завершённое изменение;
- объясняет каждый шаг по мере его выполнения.

**Этапы:**
1. Приветствие и анализ кодовой базы.
2. Поиск возможности для улучшения.
3. Создание изменения (`/opsx:new`).
4. Подготовка предложения.
5. Создание спецификаций.
6. Подготовка проектного решения.
7. Создание задач.
8. Реализация задач (`/opsx:apply`).
9. Проверка реализации.
10. Архивация изменения.
11. Итоги и следующие шаги.

**Example:**
```
Вы: /opsx:onboard

ИИ:  Добро пожаловать в OpenSpec!

     Я проведу вас через весь процесс на вашей кодовой базе.
     Мы найдём небольшое улучшение, создадим для него изменение,
     реализуем его и отправим в архив.

     Сейчас поищу в кодовой базе возможности для улучшения...

     [Analyzes codebase]

     Нашёл несколько задач:
     1. Добавить проверку данных в контактную форму
     2. Улучшить сообщения об ошибках при аутентификации
     3. Добавить состояния загрузки для асинхронных кнопок

     Что вам интересно? (Или предложите другой вариант.)
```

**Советы:**
- подходит новым пользователям для освоения процесса;
- использует настоящий код, а не учебные примеры;
- создаёт реальное изменение, которое можно сохранить или отменить;
- занимает 15–30 минут.

## Синтаксис команд в разных ИИ-инструментах

В разных ИИ-инструментах синтаксис команд немного отличается. Используйте формат для своего инструмента:

| Файл команды в вашем инструменте | Пример синтаксиса | Примеры инструментов |
|--------------------------|----------------|---------------|
| `.../commands/opsx/<id>.*` | `/opsx:propose`, `/opsx:apply` | Claude Code, Gemini CLI, Crush |
| `.../opsx-<id>.*` | `/opsx-propose`, `/opsx-apply` | Cursor, Devin Desktop, Copilot (IDE), Trae, Oh My Pi |
| отсутствует — только навыки | `/openspec-propose`, `/openspec-apply-change` | CodeArts, ForgeCode, Hermes, MiniMax Code, Mistral Vibe, Zed Agent, общий `.agents` |
| отсутствует — Kimi Code | `/skill:openspec-propose` | Kimi Code |
| отсутствует — Codex CLI | `$openspec-propose` | Codex |

> **Devin Desktop и Devin Local:** файлы `.devin/workflows/opsx-*.md` позволяют
> использовать в Devin Desktop команду `/opsx-propose`. В Devin Local рабочих
> процессов нет — используйте навыки из `.devin/skills/`, например
> `/openspec-propose`, работающие в обоих агентах.

Назначение команд одинаково во всех инструментах, но отображение зависит от интеграции. В разделе [Вызов команд](/ru-RU/supported-tools/#вызов-команд) перечислены все поддерживаемые инструменты; в этой таблице приведены только примеры каждого формата.

> **Примечание:** команды GitHub Copilot (`.github/prompts/*.prompt.md`) доступны только в расширениях IDE (VS Code, JetBrains, Visual Studio). GitHub Copilot CLI пока не поддерживает пользовательские файлы запросов; подробности и обходные решения см. в разделе [Поддерживаемые инструменты](/ru-RU/supported-tools/).

## Устаревшие команды

Эти команды используют прежний рабочий процесс «всё сразу». Они по-прежнему работают, но рекомендуется использовать команды OPSX.

| Команда | Назначение |
|---------|--------------|
| `/openspec:proposal` | Создать все артефакты сразу (proposal, specs, design, tasks) |
| `/openspec:apply` | Реализовать изменение |
| `/openspec:archive` | Архивировать изменение |

**Когда использовать устаревшие команды:**
- существующий проект уже использует старый рабочий процесс;
- изменение простое и поэтапное создание артефактов не требуется;
- вы предпочитаете подход «всё или ничего».

**Переход на OPSX:**
Продолжайте работу над устаревшими изменениями командами OPSX. Структура артефактов совместима.

## Устранение неполадок

### «Изменение не найдено»

Команда не смогла определить, с каким изменением работать.

**Решения:**
- явно укажите имя изменения: `/opsx:apply add-dark-mode`;
- проверьте, существует ли папка изменения: `openspec list`;
- убедитесь, что вы находитесь в каталоге нужного проекта.

### «Нет готовых артефактов»

Все артефакты либо завершены, либо заблокированы из-за отсутствующих зависимостей.

**Решения:**
- запустите `openspec status --change <name>`, чтобы узнать, что блокирует работу;
- проверьте, существуют ли обязательные артефакты;
- сначала создайте недостающие артефакты-зависимости.

### «Схема не найдена»

Указанной схемы не существует.

**Решения:**
- выведите список доступных схем: `openspec schemas`;
- проверьте написание имени схемы;
- если схема пользовательская, создайте её командой `openspec schema init <name>`.

### Команды не распознаются

ИИ-инструмент не распознаёт команды OpenSpec.

**Решения:**
- убедитесь, что OpenSpec инициализирован: `openspec init`;
- повторно создайте навыки: `openspec update`;
- проверьте, существует ли каталог `.claude/skills/` (для Claude Code);
- перезапустите ИИ-инструмент, чтобы он обнаружил новые навыки.

### Артефакты создаются неправильно

ИИ создаёт неполные или некорректные артефакты.

**Решения:**
- добавьте контекст проекта в `openspec/config.yaml`;
- задайте специальные правила для отдельных артефактов;
- подробнее опишите изменение;
- используйте `/opsx:continue` вместо `/opsx:ff`, чтобы лучше контролировать процесс.
